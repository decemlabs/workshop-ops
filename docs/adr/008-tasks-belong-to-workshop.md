# ADR-008: Задача принадлежит цеху, исполнитель — сменная роль

## Контекст
Изначально у задачи был только исполнитель (`Task.worker`), а цех задачи вычислялся через
`task.worker.workshop`. Работа цеха оказывалась привязана к людям: перевели рабочего —
задачи уехали за ним в другой цех, удалили рабочего — задачи цеха исчезли вместе с ним.
Счётчики карточки цеха считались через `worker__workshop`, то есть показывали не работу
цеха, а работу его нынешних людей.

## Решение
У задачи собственный обязательный `Task.workshop`, а `Task.worker` стал необязательным:
задача может лежать в цехе и ждать, кому её отдадут. Добавлено одно поле `Task.former_worker`
— прежний исполнитель. Историю переводов отдельной моделью не заводили.

Правила:
- каждая задача принадлежит ровно одному цеху, цех задачи при переводах не меняется;
- у рабочего один текущий цех (`Worker.workshop`) — как и было;
- назначить задачу можно только действующему рабочему **из цеха задачи**
  (`TaskSerializer.validate` для API и `Task.clean()` для админки);
- перевод рабочего и его удаление открепляют задачи: `former_worker = worker, worker = NULL`.

## Причины
- `former_worker` закрывает сразу два требования одним полем: у выполненной ничьей задачи
  видно, кто её выполнил, и известно, кому её вернуть.
- Откат кнопки «Вернуть» получается следствием правила, а не снимком состояния на клиенте:
  *задача возвращается прежнему исполнителю, когда тот снова работает в её цехе и задачу за
  это время никто не взял* (`release_tasks` / `return_tasks` в `views.py`). Это работает
  одинаково для обратного перевода и для восстановления удалённого рабочего.
- Проверку «исполнитель из цеха задачи» держим на уровне приложения: в Postgres она
  потребовала бы составного внешнего ключа или триггера, а соседнее правило про уволенного
  рабочего и так живёт в сериализаторе.

## Последствия
`Task.worker` бывает `NULL`, поэтому обходы связей это учитывают. В частности,
`SoftDeleteMixin.restore` поднимает за задачей её **цех**, а не её рабочего: владеет задачей
цех, и воскрешать уволенного ради восстановления задачи не нужно — задача вернётся в цех
ничьей и подождёт нового исполнителя.

Удаление рабочего больше не уносит задачи цеха: они остаются активными и видны в загрузке
цеха. Удаление цеха по-прежнему гасит всё одной партией — там открепления нет, потому что
цех восстанавливается целиком.

Перевод рабочего есть в двух местах — `bulk-move` и обычная правка рабочего
(`WorkerViewSet.perform_update`), потому что цех у рабочего меняется и через форму. Оба
пути обязаны открепляться одинаково, иначе задача останется в цехе A с исполнителем из цеха B.
